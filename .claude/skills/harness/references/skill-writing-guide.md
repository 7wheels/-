# 스킬 작성 가이드

## 1. Description 작성 패턴

Description은 스킬의 유일한 트리거 메커니즘이다.

**작성 원칙:**
1. 스킬이 하는 일 + 구체적 트리거 상황 모두 기술
2. 유사하지만 트리거하면 안 되는 경우의 경계 조건 명시
3. 약간 "pushy"하게 — Claude의 보수적 판단을 보상

**좋은 예:**
```yaml
description: "PDF 파일 읽기, 텍스트/테이블 추출, 병합, 분할, 변환 등 모든 PDF 작업.
  .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것."
```

**나쁜 예:**
- `"데이터를 처리하는 스킬"` — 너무 모호
- `"PDF 관련 작업"` — 트리거 상황 미기술

## 2. 본문 작성 스타일

### Why-First 원칙
이유를 이해하면 엣지 케이스에서도 올바르게 판단한다.

**나쁜 예:** `ALWAYS use pdfplumber. NEVER use PyPDF2.`

**좋은 예:** `테이블 추출에는 pdfplumber를 사용한다. PyPDF2는 행/열 구조를 보존하지 못하기 때문이다.`

### 일반화 원칙
특정 예시에만 맞는 수정 대신 원리 수준에서 일반화한다.

### 명령형 어조
"~합니다" 대신 "~한다", "~하라" 형태 사용.

### 컨텍스트 절약
- "Claude가 이미 알고 있는가?" → 삭제
- "이 설명 없으면 실수하는가?" → 유지
- "예시 하나가 긴 설명보다 효과적인가?" → 예시로 대체

## 3. Progressive Disclosure 패턴

```
skill-name/
├── SKILL.md (개요 + 주요 흐름, 500줄 이내)
└── references/
    ├── domain-a.md
    └── domain-b.md
```

사용자 요청에 맞는 reference만 로드.

---

## 4. 스킬 크기 제한

- SKILL.md: 500줄 이내
- 초과 내용: `references/`로 분리
- 300줄 이상 reference: 상단에 목차 포함

---

## 5. 스킬에 포함하지 않을 것

- README, CHANGELOG 등 부가 문서
- 스킬 생성 과정의 메타 정보
- 사용자 대상 설명서
- Claude가 이미 알고 있는 일반 지식
